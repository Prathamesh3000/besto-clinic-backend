### Task Progress

**Task Name:** MongoDB to PostgreSQL migration — Phase 0 foundation

**Description:**
Convert the BestoClinic backend from MongoDB to PostgreSQL. Phase 0 is the approved 3-day foundation
stage: assess true scope, decide the tenant-isolation model, profile the real data, design the relational
schema, build a verified data migration for one clinic, and port two modules end to end to establish a
proven pattern. The full programme is separately estimated at approximately 121 developer-days and is
**not** part of this 3-day scope.

**Previous Status:**
Not applicable — first day of this task.

**Today's Work Completed:**

1. **Scope assessment completed and documented** (`SQL_MIGRATION_PLAN.md`). Measured the actual conversion
   surface from the codebase rather than estimating: 74 collections, 166 files touching the data layer,
   ~1,200 query call sites, 291 `populate()` joins, 95 aggregation pipelines, 237 embedded array fields,
   213 foreign-key references, 225 indexes, 83 schema hooks.
2. **Architecture decisions finalised and recorded** — PostgreSQL as the engine, Knex with a repository
   layer for data access, schema-per-clinic with per-tenant database roles for isolation, and incremental
   per-clinic cutover.

   its rationale, four binding implementation rules, and the CI guards that enforce them.

   binary, each a single command, plus exit gates for the 7 later phases. Work stops when a gate is red.

   available for browsing data.
6. **CP-0 (Environment gate) built and PASSED.** Includes safety guards that refuse to run schema changes

**Blockers / Dependencies:**

Three findings require a business decision before the affected tables can be designed. They do **not**
block the other ~60 tables, so work continues in parallel.

1. **2,191 patient-ledger records reference patients that no longer exist.** Verified against the tenant
   database, the platform patient records and the user records — no match in any. This is financial data
   and every row would be rejected by the new database constraints. *Need to know whether these are real
   entries whose patients were lost, or leftover demo data.*
2. **`videosessions` collection is empty**, so 77 chat messages and 8 emergency sessions reference records
   that do not exist. This confirms a previously reported issue (bug #29). *Need agreement to make these
   columns optional, which appears correct as the sessions were never created.*
3. **`proceduretemplates` holds 16 live records but its schema file fails to load** (it references a
   constant that does not exist in the codebase). Without a decision this data would be lost during
   migration. *Need to know whether to migrate it or formally retire it.*

**Additional item raised separately (not a blocker):** tenant database credentials for all 27 clinics are
stored **unencrypted** in the platform database, despite the code comments and handover documentation
stating they are encrypted. The encryption helper exists but is applied only to the cache copy. Recommend
raising this as its own security ticket rather than absorbing it into the migration.
