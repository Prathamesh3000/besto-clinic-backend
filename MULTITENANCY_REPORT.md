# BestoClinic — Multi-Tenancy Audit Report

**Scope:** tenant isolation, provisioning, per-tenant data integrity, shared-collection
scoping, connection pooling.
**Method:** static analysis of the full `src/` tree **plus** live cross-tenant attack
tests executed against the real Express app and the production Atlas cluster.

---

## Executive summary

**Tenant isolation is sound. Tenant *provisioning* is completely broken.**

The client's report that "multi-tenancy is not working perfectly" is correct, but not
for the reason one would fear. No data leaks between clinics — I attacked it directly
and every attempt was blocked. The actual failure is that **you cannot successfully
onboard a new clinic through the product**. Every attempt has failed, in exactly the
same way, since the feature was built.

| Area | Verdict |
|---|---|
| Cross-tenant data isolation | ✅ **11/11 attacks blocked** |
| Tenant slug validation | ✅ Rejects spoofing, traversal, empty, missing |
| Shared platform collections | ✅ Scoped (one leak found and fixed — see §3) |
| Connection pooling | ✅ Adequate headroom |
| **Tenant provisioning** | ❌ **9 of 9 attempts failed — 100% failure rate** |
| **Per-tenant completeness** | ❌ **7 "active" clinics have zero users** |

**Only 2 of 19 clinics are actually usable.**

## 1. The critical bug — tenant provisioning has never worked

### Evidence

Every `ProvisioningStatus` record in the database is `failed`, all at the same step:

```
── hitayu-general-clinic
   _adminPassword   completed
   creating_db      failed  ERR: connect ECONNREFUSED 127.0.0.1:27017
── jj-clinic-wq1m          (identical)
── kk-clinic-u5x2          (identical)
── kk-clinic               (identical)
── jj-clinic               (identical)
── apollo-hospitals-btm    (identical)
── sunrise-health-clinic-q8pu (identical)
── sunrise-health-clinic-aiai (identical)
── sunrise-health-clinic   (identical)
```

**9 records, 9 failures, one cause.**

### Root cause

`src/modules/productOwner/tenant.service.js` → `_generateDbUri()`:

```js
const dbHost = process.env.TENANT_DB_HOST || 'localhost:27017';   // ← the bug
return `mongodb://${dbHost}/${dbPrefix}_${slug}`;
```

`TENANT_DB_HOST` is **not set** in `.env` — and wouldn't be in any deployment that uses
Atlas. So every clinic created through the app was assigned a database on
`localhost:27017`, where no MongoDB is running. Provisioning died immediately at
`creating_db` and the clinic was left stranded in `pending`.

The contrast makes it unmistakable:

| Created by | Resulting URI |
|---|---|
| `scripts/seed-platform-full.js` (**works**) | `mongodb+srv://…@cluster0…/bestoclinic_smilecare_dental?appName=Cluster0` |
| The application itself (**fails**) | `mongodb://localhost:27017/bestoclinic_sunrise-health-clinic` |

Two differences: the wrong host, and hyphens kept where the working format underscores
them. The seed scripts derive the URI from `PLATFORM_DB_URI`; the product's own
provisioning path did not.

> This is why clinics you seeded by script work and clinics onboarded through the UI
> never do. It is the single highest-impact defect in the system.

### Fix applied

`_generateDbUri()` now derives from `PLATFORM_DB_URI`, inheriting host, credentials and
connection options, and normalises the database name to underscores. An explicit
`TENANT_DB_HOST` still overrides, for deployments that put tenants on a separate cluster.

**Verified:**

```
stored URI of a known-working tenant : mongodb+srv://…/bestoclinic_smilecare_dental?appName=Cluster0
regenerated by the fixed function    : mongodb+srv://…/bestoclinic_smilecare_dental?appName=Cluster0
IDENTICAL                            : YES

newly derived URI -> connect + ping  : OK   (creating_db would now succeed)
```

### ⚠️ Still unverified downstream

All 9 failures died at step 1 of 5. The remaining steps —
`generating_clinic_code → seeding → creating_admin → applying_plan` — have **never
executed successfully in production**. They are unproven, not proven-good. The next
action after deploying this fix must be to **onboard one test clinic end-to-end** and
watch every step complete.

## 2. Tenant isolation — attacked and held

Live tests against the real app, tenant **A = jathar-dental**, tenant **B = smilecare-dental**.

| # | Attack | Result |
|---|---|---|
| T1 | A's token + B's `x-tenant-id` header | **403** "Tenant mismatch — your token belongs to a different tenant" |
| T2 | Read B's patient by id, as A | **404** |
| T2 | Read B's appointment by id, as A | **404** |
| T3 | Read B's job posting by id, as A | **404** |
| T3 | List B's job applications, as A | **404** |
| T3 | Departments list leaking B's departments | **Blocked** — A sees only its own 3; B's `Reception`/`Nursing` absent |
| T4 | Nonexistent tenant slug | **404** |
| T4 | Path traversal `../admin` | **404** |
| T4 | Empty slug | **400** |
| T4 | Missing `x-tenant-id` header | **400** |
| T6 | Connection pool headroom | **PASS** |

**11 passed, 0 failed.**

The isolation model is genuinely well built:

- **Database-per-tenant.** Each clinic has its own MongoDB database, so a leak requires
  connecting to the wrong database entirely — not merely forgetting a `WHERE` clause.
- **JWT ↔ header cross-check.** `tenantResolver` compares the slug in the token against
  the `x-tenant-id` header and rejects mismatches ([tenantResolver.js:43](src/middleware/tenantResolver.js#L43)).
- **Slug sanitisation.** Regex-validated, lowercased, fail-closed.
- **Encrypted URIs at rest.** Tenant `dbUri` is AES-encrypted and `select: false`.
- **Every tenant router** calls `tenantResolver()` — verified across all route files.

## 3. Shared platform collections — the real risk surface

21 collections are **shared across all tenants** and therefore depend on an explicit
clinic filter in code, with no database boundary as a safety net:

```
CalendarFeedToken, Clinic, CreditTransaction, CreditWallet, FeaturedDoctor,
FeatureFlag, GuestScan, Integration, JobApplication, JobPosting, Plan,
PlatformPatient, PlatformUser, PrescriptionScan, Promotion, ProvisioningStatus,
Rebate, Subscription, TenantAuditLog, UserDirectory, WebhookEvent
```

I audited every tenant-facing query against these. All are scoped via `_resolveClinic(tenantSlug)`:

- `listClinicJobPostings` → `{ clinic: clinic._id }` ✅
- `listApplicationsForJob` → `{ jobPosting: jobId, clinic: clinic._id }` ✅
- `getApplicationResume` → `{ _id, clinic: clinic._id }` ✅

**One genuine leak was found and fixed:** `getDistinctDepartments()` had **no clinic
filter at all** — it returned department names from every clinic on the platform. It was
latent rather than exploited only because it also filtered to `status: ACTIVE`, and no
clinic has a published job yet. The moment one did, clinics would have started seeing
each other's department names. Now scoped per tenant.

> **Standing risk:** these collections have no structural protection. A future query
> that forgets `clinic: clinic._id` leaks across tenants silently. Recommend a code-review
> rule: *any* query against a platform model from tenant-facing code must include a clinic
> filter.

### Accepted design exposure

`POST /public/lookup-email` returns `clinicId`, `clinicName`, `clinicCode` and `role` for
any email address. This is deliberate — it powers email-first login — but it does let an
attacker enumerate which clinic an email belongs to. Rate limiting is the only control.
Acceptable, worth knowing.

**Seven clinics are marked `active` but contain zero users.** They have valid database

seeding step.

## 5. Connection pooling

```
MAX_TOTAL_CONNECTIONS = 50      MAX_POOL_SIZE = 5 per tenant
IDLE_TIMEOUT_MS       = 30 min  active clinics = 9
```

Adequate today. Worth noting for growth: the ceiling is **50 tenants per process**, and
worst-case sockets to Atlas is **50 × 5 = 250**. Beyond ~50 active clinics the LRU
eviction in `_pruneOldest()` will start thrashing — connections evicted and immediately
re-opened. Fine for now; revisit before onboarding at scale.

The manager itself is well built: in-flight promise deduplication prevents duplicate
connections under concurrency, and a circuit breaker isolates a failing tenant DB.

## 6. Separate finding — unhandled async errors

While testing I hit a request that **hung forever** rather than returning an error.

**Cause:** Express 4 does not catch rejected promises from `async` route handlers. Three
modules registered bare `async` controllers with no `asyncHandler` wrapper, so *any*
error on those routes — not found, permission denied, validation — left the request
open until the browser timed out. The user sees "nothing happens".

| Module | Routes affected |
|---|---|
| `jobPortal` (tenant) | 11 |
| `jobPortal` (public — incl. careers application submit) | 3 |
| `credit` | 5 |
| `holiday` | 5 |

**24 routes total.** All now wrapped and verified: the previously-hanging route returns
`404 "Application not found"`.

This is very likely a contributor to the recruitment bug reports — a failure that hangs
is indistinguishable from a dead button.

## 7. Recommendations, in priority order

1. **Deploy the provisioning fix and onboard one test clinic end-to-end.** Watch all five
   steps complete. Steps 2–5 have never run successfully in production.
2. **Decide what to do with the 10 `pending` clinics.** They have unreachable URIs stored.
   Either re-run provisioning for them (`registration.service.js` already supports retry
   from `failed`) or delete them — they are noise in the platform admin.
3. **Create admin users for the 7 empty `active` clinics**, or mark them inactive. Right
   now they misrepresent the platform's state.
4. **Add a code-review rule** for platform-model queries in tenant-facing code: a clinic
   filter is mandatory. This is the one place where the architecture offers no safety net.
5. **Add an integration test for tenant isolation.** The suite I wrote can be adapted —
   it takes seconds to run and would catch a regression in the isolation model immediately.
6. **Revisit connection limits before ~50 active tenants.**
